# Score YAML を正本にする計画

Score YAML を、曲を打ち込む唯一の方法にする。設計担当と実装担当が同じ1ファイルを順番に書き、Riffra のプロジェクトはそこから作られる派生物にする。GUI で直した内容も YAML に戻す。

担当とフェーズの手順は `agents/skills/composition/references/score-workflow.md`。

この文書の「仮決定」は、作業を始めるためのたたき台であり、確定した仕様ではない。各段階の作業に入るときに見直し、実装や試作で分かったことに合わせて変えてよい。変えたら、この文書を更新する。

---

## 前提

ユーザーと合意している方針。仮決定はこの範囲で考える。

| 方針                   | 内容                                                                                                |
| ---------------------- | --------------------------------------------------------------------------------------------------- |
| 正本は1ファイル        | 設計も実装も同じ `score.yaml` に書く                                                                |
| YAML が完全な正本      | GUI で直した内容も YAML に戻す。難しい範囲が出たら、そこで別の方式を考える                          |
| 機能は Riffra に足す   | Sonalloy には DAW の機能がないので、VST3・ミックスなどは Riffra の拡張にする                        |
| Sonalloy でも読める    | Riffra 用の YAML を Sonalloy でも開ける程度の互換を保つ                                             |
| 解析コードは両方に持つ | Riffra と Sonalloy は同じ解析コードを持つ（意図したもの）。解析を変えるときは両方に同じ変更を入れる |
| 欲しい音               | 設計担当が自然言語で書く。実装担当は、それを満たす音源の選定と音作りを行う                          |
| 用語                   | `preset` / `definition` で指定する音源を「内蔵音源」と呼ぶ                                          |

| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 仮決定

### 全体

| 仮決定              | 内容                                                                                                                                                                                                 | 理由                                                                                                                                                                                                  |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 拡張の扱い          | 新しい機能は Riffra の拡張として足す。拡張の項目は仕様に列挙する。Sonalloy は列挙された項目を認識して無視し、項目の種類ごとに1回だけ警告を出す。列挙にない未知の項目は、今と同じく両方でエラーにする | Sonalloy にはエフェクトやミックスを解釈する場所がない。Riffra 用の YAML を Sonalloy でも鳴らせれば、設計担当が DAW なしで聴き直せる。未知の項目をエラーにする厳しさは、打ち間違いを見つけるために残す |
| 仕様書の置き場      | Riffra の文法と拡張は `docs/score-yaml.md` に記載し、Sonalloy と共通する文法は互換性を保つ                                                                                                           | 意味を持つのは Riffra だけなので、説明も Riffra に置く                                                                                                                                                |
| YAML に入れないもの | トランスポート（ループ範囲、パンチ、メトロノーム、カウントイン）、選択・表示、マーカー、ミュート・ソロ、録音待機・モニター、オーディオデバイス。作り直しても残す                                     | 聴く・作業するための一時的な状態で、曲の中身ではない。曲の出入りは `part_window` などで YAML に書く                                                                                                   |

### 楽器

| 仮決定               | 内容                                                                                                                                                                                                                                                                                                        | 理由                                                                                                                                                                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 内蔵音源と本番の音源 | 内蔵音源（`preset` / `definition` / `external`）とは別に、Riffra で鳴らす本番の音源を `source` に書く。`source` があれば内蔵音源は省略できる。内蔵音源のない楽器は Sonalloy では鳴らさずに警告する。手順では、設計担当が必ず内蔵音源を書き、実装担当はそれを消さない                                        | GUI で VST3 のトラックを作ったときなど、内蔵音源を決めようがない場面がある。必須にすると、意味のない値を推測して埋めることになる。互換は手順の側で保つ                                                                                 |
| 欲しい音の項目       | `sound` に自然言語で書く。`role` と同じく演奏には効かない。拡張ではなく共通の項目にする                                                                                                                                                                                                                     | 設計担当は Sonalloy でも同じファイルを開く。拡張にすると毎回警告が出るだけになる                                                                                                                                                       |
| VST3 の指定          | `source.vst3` に、プラグイン名、丸ごと読み込む状態（`state`）、状態の一部の書き換え（`patch`）、パラメーター（`params`）を書く。`state` と `patch` は同時に書ける。パスは Score ファイルからの相対パス                                                                                                      | このPCの VST3 の鳴らし方は、丸ごと読み込む（Pianoverse・MODO）、一部を書き換える（SampleTank・AmpliTube）、パラメーターを送る（Surge XT）の3通りで、これで全部書ける。プラグインを名前で指定すると、パスより読みやすく、別のPCでも通る |
| ドラムキット         | `kits` に音源を1つ書き、部品の楽器から `kit` で参照する。キットは1つのトラックになり、属する楽器は自分の `source` と `effects` を持てない。部品の `gain_db` と `pan` は内蔵音源で鳴らすときだけ効き、キットの中の音量差はプラグインの状態で付ける。Sonalloy は `kit` を無視し、各部品が自分の内蔵音源で鳴る | AD2 と MODO DRUM は1つのインスタンスで全部品を鳴らす。部品ごとに別インスタンスにすると、重いうえにルームやブリードが成り立たない                                                                                                       |
| 演奏ごとの `gain_db` | 今と同じく別トラック・別インスタンスにする。`source` を持つ楽器でこれが起きたら、検証で警告する                                                                                                                                                                                                             | 重なって鳴る演奏の音量を別々に付けるには、トラックを分けるしかない。演奏ごとの `gain_db` は実装担当が付けるので、重い音源で増えたときに自分で判断できる                                                                                |
| ベロシティの補正     | 折れ線の対応 `velocity: [[入力, 出力], ...]` だけにする。入力は 1〜127 を覆い、出力も 1〜127 に収める                                                                                                                                                                                                       | 折れ線ならオフセットも曲線も表せ、範囲外が構造上起きない                                                                                                                                                                               |
| ライブラリの参照     | 音源・エフェクトは Score に直接指定し、State と WAV は曲フォルダに置く。                                                                                                                                                                                                                                    | 再構築は曲フォルダを明示して行う                                                                                                                                                                                                       |
| 録音と効果音         | `audio: true` の楽器を作り、セクションの `audio_clips` に音声ファイルを置く。音声ファイルは曲のフォルダの `audio/` に置く。Sonalloy はこの楽器とクリップを無視する                                                                                                                                          | YAML を完全な正本にするには、録音や効果音も YAML で表せる必要がある                                                                                                                                                                    |

書き方の案:

```yaml
instruments:
  bass:
    role: 低音と推進力
    sound: 指で弾いた丸いエレキベース。キックの居場所は取らない
    preset: BASS/013-soft-round-bass
    source:
      vst3:
        plugin: MODO BASS 2
        state: states/bass.json
        patch: [{ path: '...', value: '...' }]
        params: { 'FX Type': { display: Phaser } } # 文字列は表示値、数値は 0〜1
      velocity: [[1, 20], [127, 118]]
  kick: { preset: DRUM/013-soft-round-kick, kit: drums, trigger_note_midi: 36 }
  take: { audio: true }
kits:
  drums:
    source: { vst3: { plugin: Addictive Drums 2, state: states/ad2.json } }
sections:
  walk:
    audio_clips:
      - {
          instrument: take,
          file: audio/take-03.wav,
          at: { bar: 1, step: 1 },
          offset_seconds: 0.25,
          duration_seconds: 8,
          gain_db: -3,
          fade_in_seconds: 0.01,
        }
```

### 奏法と制御

| 仮決定               | 内容                                                                                                                                                                                                                                           | 理由                                                                                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 奏法の書き方         | 名前付きの奏法は、区間のイベント `kind: articulation` で書く。トークンに付ける書き方は作らない                                                                                                                                                 | このPCの VST3 の奏法は、キースイッチや CC で状態を切り替える仕組みで、区間が実際の動きに合う。1音だけの奏法も1音ぶんの区間で書ける。トークンの書き方を足すと、`^ ! _` との組み合わせの規則が増える |
| 奏法の名前           | 仕様で決めた語彙だけを使う。最初は今の音源が実際に持つ `mute`、`dead`、`slide`、`hammer`、`harmonic`。新しい奏法は仕様に足してから使う                                                                                                         | 自由な名前にすると `mute` と `palm_mute` のような揺れが出て、音源との対応が抜ける                                                                                                                  |
| 音源との対応         | `source.articulations` に、奏法名とキースイッチ・CC の対応を書く。`default` は区間の後に戻す奏法                                                                                                                                               | 対応は音源ごとに違うので、音源の側に書く                                                                                                                                                           |
| キースイッチの出し方 | 区間の開始の 1/32 拍前にキースイッチのノートを出し、区間の終わりまで押し続ける。終わったら `default` を同じように出す。CC の奏法は、区間の始まりで値を送り、終わりで `default` に戻す。対応のない奏法名は Riffra ではエラー、Sonalloy では無視 | MODO には、押している間だけ効くキースイッチと、押すと切り替わるキースイッチがある。少し前から終わりまで押し続ければ、どちらでも効く。終わりに既定へ戻せば、状態が後ろへ漏れない                    |
| CC                   | 点は `{kind: cc, instrument, number, value}`（0〜127）。変化は既存の `automation` で `control: "cc:<番号>"` と書く                                                                                                                             | 奏法の一部やエクスプレッションは CC でしか届かない。既存の `automation` を広げれば、新しい書き方を覚えなくてよい                                                                                   |

書き方の案:

```yaml
events:
  - { kind: articulation, instrument: bass, name: mute, at: { bar: 2, step: 1 }, duration_steps: 8 }
instruments:
  bass:
    source:
      articulations:
        default: { keyswitch: 24 }
        mute: { keyswitch: 26 }
        harmonic: { cc: { number: 64, value: 127 } }
```

### 歌

| 仮決定     | 内容                                                                                                                                                                                                                                                                                         | 理由                                                                                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 歌詞       | 最上位の `lyrics` に素材として置き、旋律パートの `lyrics` で当てる。空白で区切った1つが、1回の発音（弱起を含め、展開後の発音の順）に当たる。数が合わなければエラー。旋律パートの `lyrics` は、名前1つか、セクションの出現ごとの名前のリスト。長音の「ー」や促音の書き方は VoiSona に合わせる | 1番と2番は旋律もセクションも同じで、歌詞だけが違う。出現ごとのリストにすれば旋律を複製せずに済む。旋律を直したときに、数のずれとして検出できる            |
| 歌の表現   | アクセント・スタッカートは既存の `^` / `!`、スラーは既存の `~` を使う。ブレス（`kind: breath`）、強弱記号（`kind: voice_dynamics`、0〜10）、ファルセット・がなり（`kind: voice_style`）はイベントで書く。ベロシティと `dynamics` は歌には効かない。音程・音量の曲線は扱わない                | 意味が同じ記号は使い回すのが覚えやすい。VoiSona の強弱はフレーズ全体を変える印なので、音符ごとに換算するとフレーズが崩れる。曲線は VoiSona が自動で付ける |
| 歌声の音源 | `source.voisona` に声と全体のパラメーター（TUNE・VIA・VIF・ALP・HUS）を書き、Riffra が状態を作る。全体のパラメーターは実装担当、音符ごとの表現は設計担当                                                                                                                                     | 全体のパラメーターは声質の調整で、音作りにあたる。音符ごとの表現は歌い方そのもの                                                                          |
| 空回し時間 | 書き出し前の空回しを、Riffra が `10 + 0.04 × 音符数` 秒に自動で設定する                                                                                                                                                                                                                      | 実測では 79 音で 10 秒、235 音で 15 秒あれば歌い切った。書き出しのたびに設定する手間をなくす                                                              |

書き方の案:

```yaml
lyrics:
  verse1: 'は し り が き の ー ま ま で'
  verse2: '...'
sections:
  verse:
    lines:
      vocal: { instrument: vocal, melody: verse_tune, lyrics: [verse1, verse2] }
instruments:
  vocal:
    preset: LEAD/010-breathy-whistle-lead
    source:
      voisona: { voice: Chis-A, tune: 0.5, vib_amp: 1, vib_frq: 1, alpha: -2, husky: 0.1 }
```

### ミックス

| 仮決定                 | 内容                                                                                                                                                                                                                                 | 理由                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| 置き場                 | 最上位の `mix` に、トラックの出力先とセンド（`tracks`）、バス（`buses`）、サイドチェイン（`sidechain`）、オートメーション（`automation`）、マスターのエフェクト（`master`）をまとめる。楽器の `gain_db` / `pan` は今の場所のまま使う | 設計の項目と混ざらない場所にまとめる。`gain_db` / `pan` を動かさなければ、Sonalloy でもそのまま効く |
| エフェクト             | `effects` に並べる。楽器・キット・バス・マスターに置ける。プラグイン設定を直接書くか、Riffra が管理する定義を参照する。参照されるエフェクトには `id` を付ける。                                                                      | 並べ替えても参照先を維持し、音作りを再利用できる                                                    |
| サイドチェインの送り元 | 楽器 ID かキット ID。キットの1部品だけを送り元にしたいときは、その楽器をキットから外す                                                                                                                                               | Riffra はプラグインの複数出力を扱っていない                                                         |
| オートメーションの位置 | セクション名・何回目の出現か・小節とステップで書く。値は Riffra のオートメーションと同じく、数値か表示値。対象はトラックとバスの音量・パン、マスターのゲイン、センドの量、エフェクトのパラメーター                                   | セクションを伸ばしたり並べ替えたりしても、オートメーションがずれない                                |

書き方の案:

```yaml
mix:
  tracks:
    bass: { output: rhythm, sends: { room: -18 } }
  buses:
    rhythm: { kind: group, gain_db: -2 }
    room: { kind: return, effects: [{ id: reverb, vst3: { plugin: Example Reverb } }] }
  sidechain:
    - { from: drums, to: { instrument: bass, effect: duck }, level_db: 0 }
  automation:
    - target: { effect: { instrument: lead, id: verb }, parameter: Mix }
      section: walk
      occurrence: 2 # 省くと全部の出現
      interpolation: linear
      points:
        - { at: { bar: 1, step: 1 }, value: 0.1 }
        - { at: { bar: 4, step: 13 }, value: '35 %' }
  master:
    effects: [...]
```

### 担当の分け方

| 項目                                                                                                       | 担当（仮）                                     |
| ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 楽器の `gain_db` / `pan`、`part_gains`、`lines.*.gain_db`、`placements[].gain_db`                          | 実装                                           |
| `source`、`effects`、`kit`、`kits`、`mix`                                                                  | 実装                                           |
| `meta.master`（ラウドネスの目標）                                                                          | 設計（完成の条件として書き、実装担当が満たす） |
| それ以外（構成・和声・リズム・旋律・編曲・強弱・奏法・歌詞・歌の表現・内蔵音源・`sound`・`role`・`notes`） | 設計                                           |

理由: 音量の釣り合いはミックスの判断なので、セクションごとや演奏ごとの音量も実装担当に寄せる。設計担当の強弱はベロシティと `dynamics` で表す。ラウドネスの目標は、曲をどう聴かせるかという完成の条件なので設計担当に置く。

### 作り直し

| 仮決定                 | 内容                                                                                                                                                                                                                                                   | 理由                                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| ファイルとの結び付き   | プロジェクトは、元の YAML ファイルの絶対パス・確定済みの本文・外部楽器の Definition パスを持つ。ハッシュは別に保存しない                                                                                                                               | どのファイルから作られたかが分からないと、作り直しも書き戻しもできない。本文の比較で足りるため、同じ内容を二重に持たない |
| コマンド               | 新しく作るのは `riffra project import-score` / MCP `import_score`。作り直すのは `riffra project rebuild-score [--path]` / MCP `rebuild_score`。アクティブな Project だけを対象にし、`--project` は持たない。作り直しは終わるまで待ち、検証の診断を返す | 今ある入口はそのまま使い、足すのは1つだけにする                                                                          |
| ファイルの監視         | Host は、開いているプロジェクトの YAML を監視し、内容が 500 ms 安定したら作り直す。誤りがあれば直前の状態を保ち、診断を Desktop に表示する。確定済みの本文と同じなら何もしない                                                                         | 保存するだけで反映されるのが一番速い。本文の比較で、監視とコマンドが重なっても二重に作り直さない                         |
| インスタンスの使い回し | トラックは楽器 ID とレーンのゲインで見分け、前後とも1レーンだけ残る場合はゲイン変更として対応付ける。楽器の指定と参照素材が変わっていなければ、音源のインスタンスとスナップショットを使い回す                                                          | 旋律だけ直したときに、Pianoverse のような重い音源を読み込み直さない                                                      |
| 取り消し               | 作り直しの確定は履歴を区切り、以降の作業状態の変更だけを履歴に積む。YAML の書き換えを取り消す操作は、GUI から YAML へ書き戻す仕組みと一緒に段階5で作る                                                                                                 | プロジェクトだけを取り消すと、YAML と食い違う                                                                            |

### GUI で直した内容を YAML に戻す

| 仮決定                   | 内容                                                                                                                                                                                                 | 理由                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 方式                     | GUI の操作を YAML の書き換えに変えてから作り直す。プロジェクトを直接直して後から YAML を合わせる形にはしない                                                                                         | 変更の向きが常に YAML → プロジェクトの1つになり、食い違いが起きない    |
| 書き換えの部品           | 解析が持っている位置情報を使った文字列の差し替えで自作する。扱うのは、値の置き換え、マップへのキーの追加と削除、リストへの追加と削除。新しく足すマップは、1行に収まるならフロー形式（`{...}`）で書く | 書式とコメントを保つには、書き換える位置を文字単位で制御する必要がある |
| 状態ファイルの書き込み先 | 曲の音源状態は Project に保存する。共有する音源の状態は、曲への変更で上書きせず、明示的な操作で更新する。                                                                                            | 曲ごとの変更を他の曲に波及させない                                     |
| 外での編集との衝突       | 書き込む前にファイルのハッシュを確かめる。最後に読んだときから変わっていれば、先にファイルから作り直し、GUI の操作は反映しない                                                                       | エディタやエージェントの変更を黙って上書きしない                       |

操作ごとの書き戻し先（仮）:

| GUI の操作                                                       | YAML の書き換え                                              |
| ---------------------------------------------------------------- | ------------------------------------------------------------ |
| ゲイン・パン                                                     | 楽器の `gain_db` / `pan`（キットは `mix.tracks`）            |
| 出力先・センド・バス                                             | `mix.tracks` / `mix.buses`                                   |
| エフェクトの追加・削除・並べ替え・パラメーター                   | `effects`                                                    |
| VST の画面で変えた状態                                           | 参照先の状態ファイル                                         |
| テンポ                                                           | セクションの先頭なら `form[].bpm`、それ以外は `time_changes` |
| 拍子                                                             | セクションの先頭なら `form[].meter`。それ以外は受け付けない  |
| 旋律・低音の音符                                                 | その音符を生んだトークン                                     |
| ドラムの打撃                                                     | その打撃を生んだマスの文字                                   |
| コードから作られた音（`comp` / `pad` / `arp`）、ロールが作った音 | 1音ずつは直せない。コードとボイシングの欄で直す              |
| 素材にない新しい音                                               | `placements`（`degree` の1音ずつ）を足す                     |
| 新しいトラック                                                   | `instruments` に楽器を足す                                   |
| 録音したテイク                                                   | `audio/` に保存し、`audio_clips` を足す                      |

音符の書き戻しの規則（仮）:

| 場合                               | 書き戻し方                                                                                                                                                                                                                   | 理由                                                             |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 何度も使われる素材の音を直した     | 影響する場所を画面で強調し、「すべての出現」か「この出現だけ」を選ばせる。最初は「すべての出現」を選んでおく。「この出現だけ」は、`from` と `replace` で素材とセクションを分け、`form` のその出現を付け替える                | 素材の共有は設計担当の意図。分けるときも既存の仕組みだけで表せる |
| 音符を消した                       | 同じ長さの休符 `.` に置き換える                                                                                                                                                                                              | 前後の位置を変えない                                             |
| 音高を変えた                       | 元のトークンと同じ文脈（主音・`relative_to`・音域）で度数に戻す。元が `c` トークンで新しい音がコードの構成音なら `c` トークンのまま。臨時記号は、スケールの音ならその綴り、外れる音なら `score import-midi` と同じ固定の綴り | 書いた人の意図した基準を保つ                                     |
| 長さ・位置を変えた                 | ほかのトークンにかからなければ、そのトークンだけを書き換える。かかるときは、その要素を決まった形（長さは `:n`、区間の境目に `                                                                                                | `）で書き直す                                                    | 直していない部分の書き方をできるだけ保つ |
| コードから作られた音を直そうとした | 直せないようにして、コードとボイシングの欄へ案内する                                                                                                                                                                         | ボイシングの規則から外れた例外を、YAML に素直に書く場所がない    |

### 検証

| 仮決定                     | 内容                                                                                                                                                                                                      | 理由                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 検証のコマンド             | CLI `riffra score validate` / `riffra score inspect`、MCP の新しい `score` ツール。拡張の項目も確かめる（プラグインの有無、状態ファイルの有無、パラメーター名、奏法の対応、音域、知声の推奨音域とテンポ） | 拡張の項目は Sonalloy では確かめられない。読み込んで初めて誤りが分かるのでは遅い |

### 段階1: YAML を正本として扱える土台を作る

できるようになること: YAML を保存すると、同じプロジェクトが作り直される。拡張を足しても Sonalloy で読める。
最初にする理由: 以降、拡張を足すたびに Sonalloy で読めなくなるのを防ぐ。作り直しがないと、直すたびにプロジェクトが増える。

| 番号 | 作業                       | 具体的な内容                                                                                                                                                                                                                                                                                                                                                                         | 触るファイル                                                                             | 終わりの条件                                                                                           |

| 3-6  | セクション単位の書き出し   | 書き出しの範囲に `{kind: section, name, occurrence}` を足す                                                                                                                     | Riffra の書き出し             | 「walk の2回目」だけを書き出せる                                                                |
| 3-7  | セクションごとのラウドネス | YAML から作ったプロジェクトの書き出しで、`form` の出現ごとのラウドネスを結果に入れる                                                                                            | Riffra の書き出し             | 書き出しの結果に出現ごとの値が並ぶ                                                              |

確かめ方: MODO BASS 2 の奏法を多く使うベースラインの曲を作る。

### 段階4: 歌モノを YAML だけで作る

できるようになること: 歌詞と歌の表現を YAML に書け、VoiSona が歌う。
この位置にする理由: 段階2の音源の仕組みを土台にする。

| 番号 | 作業                 | 具体的な内容                                                                                                                                  | 触るファイル            | 終わりの条件                                              |
| ---- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- | --------------------------------------------------------- |
| 4-1  | 歌詞                 | `lyrics` と旋律パートの `lyrics` を足す。展開後の音符の `lyric` に入れる。数が合わないときは、セクション・出現・位置付きのエラーにする        | 両方の `score/`         | 1番と2番で違う歌詞が、同じ旋律の音符に入る                |

| 4-3  | VoiSona の状態の生成 | `voisona_state.py` の処理（音符・歌詞・表現・テンポ・拍子・全体のパラメーターから状態を組む）を Riffra に移し、作り直しのたびに状態を作り直す | Riffra                  | 歌のパートが YAML だけで歌う                              |

### 段階5: GUI で直した内容を YAML に戻す

できるようになること: YAML が完全な正本になる。
最後にする理由: 戻す先の仕様（段階2〜4）が固まってからでないと、書き戻しを作り直すことになる。

## リスク

| リスク                    | 影響                                                          | 対応                                                               |
| ------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------ |
| Pianoverse の読み込み時間 | 音源そのものを差し替えたときは使い回しが効かず、数分待つ      | 段階1の使い回しで、差し替えない限り読み込み直さない                |
| 拡張の項目が増える        | Sonalloy だけで使うときに、読み飛ばす項目が増えて分かりにくい | 仕様書で拡張を章として分け、混ぜて書かない                         |
| 解析コードが2つある       | 片方だけ直して、Riffra と Sonalloy の解釈がずれる             | 同じテスト用の YAML を両方で検証して比べる                         |

| 書き換えの部品の自作      | 1行のマップ（`{...}`）にキーを足す処理が一番難しい            | 行き詰まったら、キーを足すときだけそのマップを複数行の形に書き直す |
