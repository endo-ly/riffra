# Riffra アーキテクチャ

Riffraの中心は、保存される制作状態と、そこから一時的に作られる実行状態を分けることです。セッション、素材、履歴の正準状態はRustの中核が持ち、画面と音声エンジンは必要な情報だけを投影として受け取ります。

個々のエンティティは [データモデル](data-model.md)、プロセス間のメッセージは [IPC契約](ipc.md)、画面の責務は [共通画面構造](ui-ux-design/application-layout.md) と [Arrange画面](ui-ux-design/arrange-screen.md) に記載します。

## 1. プロセスと責務

```text
┌────────────────────────────────────────────────────────────┐
│ Tauri shell                                                │
│ React UI ── Tauri IPC ── Rust Desktop Adapter             │
│                         ├─ riffra-core                     │
│                         ├─ riffra-host                     │
│                         └─ Runtime / Job coordination       │
└───────────────┬──────────────────┬─────────────────────────┘
                │                  │
        ┌───────▼────────┐ ┌──────▼─────────┐ ┌─────────────▼──────┐
        │ riffra-audio   │ │ plugin scanner │ │ render worker        │
        │ real-time audio│ │ VST3 discovery │ │ offline rendering    │
        └────────────────┘ └────────────────┘ └─────────────────────┘
```

| 構成要素        | 持つ責務                                                                    | 正準状態                                   |
| --------------- | --------------------------------------------------------------------------- | ------------------------------------------ |
| Tauri shell     | アプリの起動、UIとの接続、Desktop Adapterとジョブの調整                     | Coreの状態を保持するが、制作規則は持たない |
| `riffra-core`   | ドメイン規則、制作操作、履歴、保存とランタイムのポート                      | `CreativeSession` と履歴                   |
| `riffra-host`   | セッション保存、素材管理、プロジェクト入出力、WAV/MIDI解析、Data Rootの所有 | ファイルと索引                             |
| Desktop Adapter | Coreのポートをデスクトップ固有の保存・音声・ジョブへ接続                    | Coreとランタイムの境界                     |
| `riffra-audio`  | デバイス、音声グラフ、プラグイン、監視、演奏、録音                          | 一時的な音声グラフ                         |
| plugin scanner  | VST3の列挙と検証                                                            | なし                                       |
| render worker   | オフライン書き出し                                                          | なし                                       |

リアルタイム音声と第三者プラグインのコードは `riffra-audio` で実行します。TauriのRustプロセスはそれを監督し、音声コールバックを直接持ちません。

## 2. 依存方向

依存はUIからホスト境界へ向かって流れます。下位の層は上位の画面や実行形態を知りません。

```text
React
  ↓ NativeApi capability
Tauri command / event
  ↓
Desktop Adapter
  ├─ riffra-core: Application / Domain / Ports
  ├─ riffra-host: Storage / Asset / Project
  └─ Runtime and Job coordination
```

### `riffra-core`

`riffra-core` はプラットフォームに依存しない制作操作の境界です。セッションの正準化、入力値の検証、履歴、素材参照、コミット順序をここで決めます。Tauri、WebView、OSのファイル、音声デバイスは直接扱いません。

### `riffra-host`

`riffra-host` はデスクトップとCLIが共有するOS境界です。`SessionStore`、Asset Repository、Project package、制作ファイルの解析、`DataRootLease` を所有します。Coreが決めた変更を保存できる形へ接続しますが、制作状態を採用する規則は持ちません。

### Desktop AdapterとCLI

Desktop Adapterは `riffra-core` とデスクトップ固有のランタイムを接続します。Standalone CLIは自身の `DataRootLease`、`SessionStore`、`AppCore<()>` を開いてCoreを直接使います。

WindowsのAttached CLIはData Rootやセッションを開きません。Desktopが公開する制御境界へ接続し、Desktop Adapterを通してGUIと同じ正準状態、履歴、音声ランタイムを操作します。CLIの利用方法と対応範囲は [ヘッドレス環境](headless-linux.md) にまとめます。

## 3. 正準状態とコミット

`CreativeSession` が、トラック、クリップ、テイク、ラック、設定、時間軸を含む永続的な制作状態の正本です。画面の選択状態やパネルの開閉、音声エンジンのグラフはセッションとは別の状態です。

制作状態を変更する操作は、次の順序で確定します。

1. Applicationが現在の正準状態から更新候補を作る。
2. Domainが参照整合性と不変条件を検証し、値を正準化する。
3. `SessionStorage` が更新候補を保存する。
4. 保存に成功したら、Coreが正準状態、履歴、正準シーケンスを更新する。
5. Desktop Adapterがライブラリ索引と音声ランタイムへ新しい状態を投影する。

検証または保存に失敗した候補は、正準状態と履歴へ入りません。処理に時間がかかる操作も、処理開始後に確定した別の編集を失わないよう、所有している変更だけを最新状態へ適用します。

## 4. ランタイム投影

音声グラフはセッションのコピーではなく、再構築できる一時的な投影です。セッションが変わるたびに、Coreが確定順序を付けたスナップショットをDesktop Adapterへ渡します。

| 段階   | 役割                                                                     |
| ------ | ------------------------------------------------------------------------ |
| 準備   | 新しいグラフとプラグイン状態を構築する。準備中は現在のグラフを使い続ける |
| 有効化 | 準備済みのグラフを再生に使う                                             |
| 破棄   | 採用されなかった準備結果を解放する                                       |

Desktop Adapterは投影を順番に処理し、古い結果が新しい状態を上書きしないようにします。投影の失敗やサイドカーの再起動が起きた場合も、保存済みの最新セッションから再構築します。

再生、停止、シークなどのTransport操作はCoreが順序を決め、Desktop Adapterが音声エンジンへ伝えます。実行中の音声グラフはセッションへ保存しません。

### Desktopの外部制御

Windows Desktopは起動時にローカルのNamed Pipeへ制御サーバーを用意し、Data Root内のdescriptorで接続先を公開します。Attached CLIはdescriptorを読み、接続とhandshakeが完了してから操作を送ります。descriptorが残っているだけでは稼働中とみなさず、接続できない場合は利用不能として扱います。

Standalone CLIはこの境界を使わず、Desktopとは別のホストとして動作します。同じData Rootを同時に開けないため、正準ファイルの競合を防げます。

## 5. 保存と回復

Data Rootは、正準セッション、世代、素材、録音、書き出し、索引をまとめる作業領域です。

```text
<data_root>/
├─ scratch/
│  ├─ current.json
│  └─ generations/
├─ library/
│  └─ riffra.db
├─ assets/
│  └─ imports/
├─ recordings/
│  ├─ inbox/
│  ├─ archive/
│  └─ library/
└─ exports/
```

`SessionStore` は新しい内容を一時ファイルへ書き込み、保存処理が完了してから現行ファイルを置き換えます。保存前の世代も残すため、プロセスが途中で終了しても現行セッションを完全な状態から復元できます。保存は同一ホスト内で直列化されます。

ロード時は、現行セッションを検証してから採用します。破損や未登録Assetへの参照が見つかった場合は、世代を新しい順に検証し、利用できる世代を回復候補にします。破損した現行ファイルは上書きしません。手動で世代を選んだ場合も、検証と正準化を通った内容だけを新しい正準状態として保存します。

DesktopとStandalone CLIは起動中 `DataRootLease` を保持します。Attached CLIはData Rootを開かず、DesktopのLeaseの所有下で制御要求だけを送ります。排他はOSのファイルロックで行い、異常終了後に残るロックファイルへ依存しません。

## 6. セーフモード、索引、ジョブ

セーフモードでは、セッションの読込とライブラリ索引の初期化だけを行い、音声デバイス、サイドカー、プラグインへ接続しません。音声や録音など外部環境を必要とする操作は利用できませんが、保存済みの制作状態の確認とオフライン処理は続けられます。

ライブラリはAssetと録音を検索するための読み取りモデルです。正本はセッションとAssetであり、索引を編集して制作状態を変更することはありません。セッション保存後の索引更新は、保存処理を待たせないよう別の処理として進みます。

VST3スキャンなど時間のかかる処理はジョブとして管理します。ジョブは開始、進行、取消、完了、失敗を状態として持ちます。レンダリングは専用ワーカーへ依頼し、音声サイドカーの常駐処理とは分離します。

## 7. Presentationの責務

フロントエンドはCoreが返したセッションを表示し、ユーザー操作をFeatureごとの `NativeApi` capabilityへ変換します。制作状態の競合解決、履歴、参照整合性、部分的なセッションマージはフロントエンドに置きません。

選択、ズーム、パネル幅、ダイアログなどの表示状態はセッションから分離します。フロントエンドは正準シーケンスを使って古い応答やイベントを表示へ適用せず、Undo/Redoの可否はCoreの履歴状態から表示します。
