# Riffra テスト戦略

テストは、制作規則を速く確かめる層から、実際の機器と画面を通す層へ広げます。下位のテストで原因を絞り、上位のテストでは利用者がたどる制作の流れを確認します。

```text
Windows実機・実音・実VST3
          ↑
アプリ全体の主要制作フロー
          ↑
Tauri / 子プロセス / ファイルの結合
          ↑
ReactとNativeApiの部品
          ↑
Coreの規則・変換・状態遷移
```

## 1. テストの層

| 層                | 主な対象                               | 確認すること                             |
| ----------------- | -------------------------------------- | ---------------------------------------- |
| Coreの単体テスト  | 制作規則、正規化、状態遷移、純粋な変換 | 正常値、境界値、失敗時の不変条件         |
| UIの部品テスト    | Reactと `NativeApi` の接続             | 操作、表示、状態反映、失敗の通知         |
| 結合テスト        | Rust、C++、Tauri、ファイル、子プロセス | 通信、保存、録音情報、Asset、ジョブ      |
| アプリ全体の確認  | Arrangeを中心とした制作フロー          | 起動、演奏、編集、保存、再読込           |
| Windows実機テスト | OS、オーディオ機器、VST3、実音         | 自動化しにくいデバイスとプラグインの挙動 |

## 2. 何をどの層で検証するか

同じ不具合を複数の層で検出できる場合は、原因に近く、実行が速い層を優先します。たとえば時間軸の正規化はCoreで確認し、画面全体のドラッグ操作はUIの部品テストで確認します。

データ消失、危険な音声、破壊的な変更には複数の境界を置きます。Coreの不変条件だけでなく、保存処理、サイドカーの安全状態、画面の復旧導線をそれぞれ確認します。

テストは内部関数の呼出し順ではなく、操作と結果を中心に書きます。内部実装を置き換えても意味が変わらないテストを残し、実装の形だけを固定するテストは増やしません。

## 3. 重点シナリオ

| シナリオ        | 成功条件                                                             |
| --------------- | -------------------------------------------------------------------- |
| セッション編集  | 操作結果が正規化され、保存後に同じ状態を読み戻せる                   |
| Assetとクリップ | 素材の参照、Audio/MIDIの配置、派生関係が保たれる                     |
| 録音            | 原音・加工音・MIDI・録音条件がテイクと一緒に回復できる               |
| ランタイム投影  | 新しい投影だけが有効になり、古い完了通知が状態を戻さない             |
| Desktop制御     | Attached CLIの操作がGUIと同じ正準状態、履歴、シーケンスへ反映される  |
| Protocol        | 不正な入力、実行失敗、競合、接続不能を異なるエラーコードで返す       |
| 保存回復        | 現行ファイルの破損時に利用可能な世代を選び、破損内容を上書きしない   |
| 音声安全        | 起動時のミュート、異常値、フィードバック、デバイス失敗を安全側へ倒す |

## 4. 実機で確認すること

CIやシミュレーションで代替できないものをWindows実機で確認します。対象は、実際のオーディオインターフェース、ドライバー、MIDI機器、VST3エディター、音声の継続性です。

実機テストでは、音が出ることだけでなく、異常時にミュートされること、設定や録音データが失われないこと、復旧方法が表示されることまで確認します。

## 5. テストを増減するときの基準

重要な利用者の行動を守らないテストは追加しません。色や余白だけの差分、内部関数を呼んだ事実だけを確認するテストは、画面や責務の変更に対して価値を持ちません。

一方で、同じ観点をより狭い層で明確に確認できる場合は、上位の重いテストを増やさず、既存テストへケースを追加します。テストの数ではなく、失敗したときに原因と影響範囲が分かることを重視します。
