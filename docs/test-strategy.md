# Riffra テスト戦略

テストの原則と、検証をどの層に置くかの判断基準を記述する。個々のテストの目録はテストコードとCIの定義が真実源であり、本書は方針を扱う。

## 1. 原則

1. **原因に近い層で確認する。** 計算や状態遷移を画面操作で繰り返さない。一方で、データ消失・危険な音声・破壊的変更には、単体と結合など異なる境界で防御を重ねる
2. **利用者の操作と結果を検証する。** ファイル名や内部関数の呼び出し順ではなく、操作とその結果を確認する。実装を置き換えても期待結果が同じなら、テストは維持される
3. **維持費に見合うテストだけ残す。** 軽微な内部変更で頻繁に壊れ、重要な欠陥を検出しないテストは減らす。色・余白・装飾の違いは自動化の対象外であり、主要操作が隠れる・重なる・到達できない問題は検出対象になる。実装と同じ計算の再現、モックの戻り値や呼び出しの確認、型システムが保証する動作の再確認は残さない
4. **同じ欠陥の検出は一つに集約する。** 複数の層やメッセージから検出できる不具合は、代表的な一つの場所で確認する。状態遷移は個別の状態ごとではなく、代表的な操作の流れで確認する
5. **失敗から原因の層が分かる粒度を保つ。** 複数の境界にまたがる機能は、層ごとに分けて確認する。一つのテストに全層を詰め込まない

## 2. 検証の層

下層ほど速く頻繁に走り、上層ほど実際の環境に近づく。

| 層            | 主な境界                     | 確認する内容                           | 実行頻度           |
| ------------- | ---------------------------- | -------------------------------------- | ------------------ |
| 単体          | 関数、状態遷移、音声処理部品 | 計算、変換、不変条件、異常値、安全条件 | 常時               |
| 部品          | React と Native API契約      | 操作、命令発行、表示、失敗、到達性     | 常時               |
| 結合          | Rust、C++、Tauri、ファイル   | 通信、保存、録音情報、索引、子プロセス | 変更領域ごと       |
| 全体簡易確認  | アプリ全体                   | 主要フローと保存復元                   | 作業単位の終端     |
| 実機(Windows) | OS、機器、VST3、実音         | 自動化で代替できない挙動               | マイルストーン終端 |

Rust側のUnit testは対象実装と同じソースファイル内に置き、別モジュールや専用ファイルへ集約しない。フロントエンドのテストは `apps/desktop/src/test/` に集約し、`app/`、`features/`、`model/`、`native/`、`shared/` の所有領域に対応する階層へ置く。FakeNativeApiとテスト用Providerは `test/support/` に置き、部品テストは `createFakeNativeApi` で作った `FakeNativeApi` を注入して呼び出し記録とイベント発火を扱う。制作規則・履歴・検証の判断はCoreのテストが担うため、部品テストが制作規則を再実装することはない。

画面をまたいで共有する状態と操作は `shared/session/` のセッションストアが持つ。そのため、アプリ全体の状態と操作は `createSessionStore(createFakeNativeApi(…))` に対してスライスを直接呼んでテストし、Nativeイベントに依存する観点は `bindSessionRuntime(store, api)` を呼んでからイベントを発火する。部品のテストは `TestSessionProvider`（または `renderWithSession`）でストアを与え、ストアの状態と操作を props で渡さない。再描画の範囲は、値を描く部品の描画回数で確認する。再生位置のように高頻度で変わる値を受け取っても、それを描かない部品が再描画されないことを、タイムラインのトラック行で固定する。

## 3. 契約の検証

RustとC++の境界契約は、生成する側と検証する側が同じフィクスチャを共有することで固定される。フィクスチャは `RIFFRA_UPDATE_CONTRACT_FIXTURES=1` のときだけ書き換わり、それ以外の実行では生成結果との一致を検査する。契約を変更したときはフィクスチャを再生成し、差分をレビューの対象にする。

| 契約               | 固定の方法                                                                                                                                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実行グラフ         | Rustが生成したフィクスチャを `contracts/execution-graph/` に置き、C++の厳格デコーダが同じファイルでデコードを検証する。欠落・未知・範囲外の入力が拒否されることも同じフィクスチャで確認する                          |
| サイドカー通信     | 全命令・全メッセージを `contracts/sidecar/` のフィクスチャで固定する。命令はRustの全 `SidecarCommand` から生成されC++で厳格にデコードされ、メッセージはC++の全エンコーダから生成されRustの型で読めることが検証される |
| 応答の単一性と相関 | 応答しない破棄で `noResponse` が返ること、2回目の応答が出力されないことはC++の `CommandResponder` で、期待と異なる応答型による即時失敗はRustの `CommandBus` とプロトコル処理で確認する                               |
| プロセス往復       | `apps/cli/tests/headless_host_process.rs` が実際の起動・接続・終了を確認する。LinuxはSafe Mode、Windowsは実サイドカーの通常モードを担当し、両環境で同じ内容を重複して確認しない                                      |

## 4. 並行性の検証

音声スレッドと制御スレッドの境界は、決定的な単体テストとThreadSanitizerで確認する。

- 単体テストでは、命令の適用、各トラックがブロックごとにちょうど1回処理されること、固定グラフのオフラインレンダーのビット一致、資源の退役と回収、診断の計算を確認する
- ThreadSanitizerの対象は、実際に複数スレッドが動くケース、オブジェクトの公開・解放が競合するケース、リアルタイムコールバックと制御処理が競合するケースに限られる。数値・MIDI内容・JSON形式・音声結果の一致だけを確認するテストは対象外である
- 抑制ファイル `tsan.supp` にはJUCE内部に起因する報告だけを理由付きで記録する。Riffraのコードに対する報告は修正し、抑制しない
- 実行するテストはスイートとケースを明示して指定する

## 5. CI の構成

| ジョブ                 | 実行内容                                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| Node                   | `format:check` / `lint` / `knip` / `typecheck` / `test`。本番のViteビルドは `main` 更新時と手動実行のみ |
| Rust host crates       | `cargo fmt --all --check`、clippy、workspaceテスト(Tauriを除く)、Safe ModeのHeadless Hostプロセステスト |
| Rust Tauri             | 空のbundle設定でclippyとテスト。パッケージングとサイドカー実行はNativeジョブで確認する                  |
| Native audio (Linux)   | ネイティブビルド、変更されたC++のclang-format、ThreadSanitizer                                          |
| Native audio (Windows) | 実サイドカーによる通常モードのHeadless Hostプロセステスト、実音比較、ネイティブテスト                   |

- 配布対象はWindowsであり、macOS向けのCIは動かさない。macOS用のC++実装とクロスプラットフォーム対応は保持する
- SidecarはCMake installで生成・配置され、installの失敗はビルドの失敗になる
- 実音・実VST3を使うテストとSlow Testは通常のPR実行から外れ、`main` 更新時と手動実行で走る
- Slow TestはCTestへ `slow` ラベルで登録し、ビルドスクリプトは環境変数が厳密に `RIFFRA_RUN_SLOW_TESTS=1` の場合だけこのラベルを実行する。長時間のループ録音ストリーミングや、全プリセットのコンパイルと発音確認が該当する
