# Composition

曲を作り始めるときから完成までを扱うSkill。

## 創作の心得（重要）

### 作業ではなく、遊びとしての創作

作曲は、依頼された仕事の処理ではない。ユーザーと一緒に良い作品を作る創作である。各段階の判断は、指示の処理としてではなく、創作の判断として行う。

遊びの心を大事にする。無難な選択を重ね続けると、破綻はなくても、何も心に響かない曲になる。

### ありきたりにしない

LLMは構造上、確率分布の平均や中央値に近い選択へ引き寄せられる。その平均を積み重ねた曲は、どこかで聴いたようで誰の心にも残らない（AI Slop）。最もありそうな選択ではなく、**あり得るけれど出てきにくい選択**を探す。平均へ向かう引力を自覚したうえで、それを外す、あるいは逆手に取る。

AI Slopの典型:

- 曲名・歌詞・コンセプトに `Glass`、`Neon`、`Midnight`、`Night` のような語ばかりが選ばれる
- アルペジオが上がって下がるだけの、初心者然とした打ち込み
- 旋律が上がって下がるだけで、跳躍がない。休符もない。**休符は一種の音符である**
- 旋律音をダイアトニックかどうかだけで選び、コードに対する摩擦や解決が設計されていない

ありきたりかどうかは、要素単体ではなく曲の中での使われ方で決まる。定番の進行やビートを使うこと自体は平均ではない。どこで、どう崩すかに作品の個性が出る。

### 局所最適ではなく、全体最適

ユーザーの指摘や自己レビューの結果に対して、その一点だけを満たすように直すと、創作としての目的が失われ、指示に従っただけの面白くない曲になる。たとえば「メロディにモチーフがない」という指摘に過剰に応えると、一つのモチーフをひたすら繰り返すだけの曲になる。

指摘は修正箇所の指定ではなく、曲の意図と響きのあいだにあるずれの指標である。判断するときは常に設計図に書いた曲の核（何を表現する曲か）に立ち返り、曲全体から見て正しい選択をする。過剰な適合は曲を平均化し、特徴を消す。

### リファレンスの位置付け

このSkillのリファレンスは、あくまで参考である。ここに書かれた語彙やパターンから選ぶことが作曲ではないし、書かれていないことをするのが禁止なわけでもない。良い曲のために必要な音、進行、リズムは、この文書の外にいくらでもある。リファレンスは判断に視点と説明を与える材料であり、選択肢の上限ではない。欲しい音がここにないなら、それを作ればいい。

## 制作の流れ

曲は、抽象度の高い決定から順に作る。音源の選定は構想と設計の後に行う。音源リストを見てから曲調を決めると、音楽が音源の在庫と得意語彙に引っ張られ、似た形に収束する。順序を守ることで、音楽の判断が音の在庫より先に来る。

1. **構想** — この曲で表現したいもの（曲の核）を言葉にする。情景、感情、物語、問いなど、手段ではなく表現の対象を書く。あわせて、エネルギーの山と谷と長さの輪郭を決める。音色や音源の名前はまだ出てこない
2. **設計図** — 核を主にどの手段で聴かせるか（旋律・グルーヴ・響き・言葉など）を決め、構成、和声の方向、パート間の関係（各区間の主役と、誰がどの帯域を支えるか）、主題の輪郭、音の世界観を書く。音の世界観は、生っぽいか電子的か、乾いているか響いているか、明暗、倍音の荒さ、年代感、パート間の対比といった音の性質の言葉で書き、音源やプリセットの名前は使わない。主に聴かせる手段が制作の軸になり、ビート主体ならリズムを、歌モノ主体なら旋律を先に鍛える。形式は [templates/blueprint-template.md](templates/blueprint-template.md)
3. **音源選定** — 設計図の音の世界観と各役割の「欲しい響き」に、音源を割り当てる。判断材料は音域・帯域・減衰の長さ・同時発音数。在庫の把握は不要な音源の作成を防ぐために必要だが、参照するのはこの段階である。カタログの読み方は riffra-headless
   - **組合せで選ぶ** — 役割ごとに候補を2〜3に絞り、組合せ全体で決める。役割ごとの最適を並べると、質感・年代感・距離感がばらばらになる。確かめるのは隣り合う役割どうしの関係で、明るさ、アタックと減衰の長さ、空間の距離が、世界観どおりに揃っているか、意図した差になっているか
   - **説明文より定義を根拠にする** — 音が聴けないAIは説明文やタグの言葉に頼りがちで、言葉の一致で選ぶと無難な形容詞を持つ音源ばかりが選ばれる。
   - **合わなければ作り、近ければ整える** — 世界観に合う候補がないときは、曲を音源に合わせて曲げず、既存の定義を土台に音源を作る。ずれが小さいときは、EQ・サチュレーション・共通の空間系で世界観へ寄せる。現在のプリセット数は非常に少ない。そのため、作りたい楽曲が既存のプリセットのみで作れる事はまずあり得ない。曲を作ったときに、その音源がすべてプリセットで作られた場合、それは手抜きとみなされる。
4. **打ち込み** — 後の要素が前の要素を参照する順に進める。次の順序は依存関係の目安であり、制作の軸に応じて入れ替えてよい。たとえば旋律が軸なら、主旋律を先に仮置きして和声と低音をそれに合わせる。各段階を確認するときは、その時点で曲として通る形に整えておく。1パートを完成させてから次へ進むと、パート間の衝突が最後に発覚して手遅れになる。強弱と音価は各パートを打ち込む時点で付ける。強弱の階層はグルーヴと旋律の表情そのものであり、後からまとめて付けるものではない。セッションの組み立ては riffra-headless

   1. 時間の器 — BPM・拍子・セクション・空クリップ
   2. 和声 — 和声イベントと伴奏
   3. 拍の骨格 — 設計図のグルーヴを担う基本セル。ドラムに限らず、拍の基準・細分・アクセントをどのパートが持つかを決める
   4. 低音 — 拍の骨格と打点を共有するか避けるかを決め、和声を結ぶ
   5. 主旋律 — 和声・グルーヴ・低音が揃った状態で判断する。合わないときは、他パートに合わせて潰すのではなく、主旋律か和声を直す
   6. 対旋律・装飾 — 主旋律の休符と長音の空白に応答する層を置く
   7. ミックス — セクション間の強弱の階層を揃え、音量・定位・空間を整えて、通して聴ける状態にする

5. **改善ループ** — 全区間を通して、多角的な観点から自己レビューする。修正するときは、パートの部分最適ではなく、編成（音域・密度・交代）、音源（世界観との一致、組合せ）、ミックス（バランス・空間）のどこに原因があるかを切り分けてから手を入れる。満足する出来になった段階でユーザーに完了報告をする。ここで終わりではなく、ユーザーから耳で聴いた指摘に応じて改善ループをさらに回す。

- 自己レビュー観点の例:
  - 曲の核が、曲から聴き取れるか
  - 平均的な選択に収まっていないか（AI Slopの典型に当たっていないか）
  - パート間の役割と音域が重なりすぎていないか
  - 展開が単調でないか
  - 強弱と音価が、グルーヴと旋律の表情になっているか
  - 指摘への修正が、曲全体を損なっていないか

## 表記

リファレンスと設計図では、音高とコードをすべて主音基準のディグリーで書き、実音名は使わない。

| 表記                          | 意味                                                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `I`〜`VII`                    | その区間の主音を `I` とした、メジャースケール上の位置。短調・モードでも同じ座標を使い、短調の基本和音は `Im・IIm7♭5・♭III・IVm・Vm・♭VI・♭VII` と書く。転調したら新しい主音を `I` とする |
| `♭` / `#`                     | 座標から半音下／半音上。`♭VII`、`#IVdim7`                                                                                                                                                |
| `Im7`、`Imaj7`、`I7(♭9)` など | 品質はローマ数字の後ろに付ける。大文字・小文字で長短を表し分けない                                                                                                                       |
| `V/VII`                       | スラッシュの右はベース音のディグリー。セカンダリードミナントは `II7 → V` のように、実際の根音と到達先で書く                                                                              |
| `R–3–5–♭7`、`3rd`、`♭9th`     | 鳴っているコードの根音を基準にした音程。構成音の列挙は `R–3–5–♭7`、個々の音は `3rd` と書く。`III7` の `III`（主音基準）とは別の座標                                                      |
| `\|`、`→`、`↔`                | 小節線、進行、往復                                                                                                                                                                       |

## 設計図の扱い

| 原則                 | 意味                                                                   |
| -------------------- | ---------------------------------------------------------------------- |
| 書いた項目だけが制約 | 記載のある項目だけを守る。未記入の項目はAIへの委任と解釈する           |
| 必須項目はない       | どの欄も空のまま始めてよい。曲名すら未定でよい                         |
| 形式は自由           | セクションの名前・数・区切り方は自由。表・箇条書き・文章のどれでもよい |
| 更新してよい         | 設計図は初期意図の記録である。制作過程で意図が変わったら書き戻す       |

設計図に書かれていないことを判断する必要があるときは、すでに書かれた意図に沿って制作側が選び、選んだ内容を設計図へ書き戻す。

[templates/blueprint-template.md](templates/blueprint-template.md) を曲ごとにコピーして埋める。書き上げた設計図は `out/` へ1曲1ファイルで置き、制作中はそのファイルを参照する。
